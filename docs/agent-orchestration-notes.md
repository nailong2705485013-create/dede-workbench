# dede工作台：Agent 编排实践笔记

> 时间：2026-11-07。来源：dede工作台从 0.2.1 到 0.4.1 的一整天改版与实测。
> 用途：一是学习笔记，记录 Agent 编排里真正踩到的问题和数据；二是记忆与交接，下次继续开发时先读第 7 节。

---

## 1. 这个项目在做什么

dede工作台是一个**本机 Agent 编排器**：它不直接调用模型 API，而是启动本机已有的两个命令行 Agent，再把它们组合起来用。

| Agent | 调用方式 | 模型 |
|---|---|---|
| Codex CLI | `codex exec --json`，用 `exec resume <id>` 续接会话 | 本机 Codex 配置（实测为 GPT，xhigh） |
| DeepSeek Harness | 安装包内的 headless CLI，加 `--json`，用 `--session-id` 续接会话 | 跟随 Harness 桌面端配置（DeepSeek V4 flash，max） |

页面上有两种用法：

- **Study**：一问一答，只用一个 Agent，可以中途切换模型。对话文件夹在 `D:\dede工作台\study\<时间>\`。
- **Work**：在指定的项目文件夹里执行任务，有三种模式：
  - 组合模式：Codex 规划 → Harness 执行 → Codex 独立审核，审核不通过最多修补 3 次；
  - 仅 Harness；
  - 仅 Codex。

## 2. 编排的核心结论（最值得记住的）

### 2.1 1 + 1 不一定大于 2
这次记账工具任务一共跑了 **29.5 分钟**：

| 部分 | 时间 | 性质 |
|---|---|---|
| 规划、执行、两次用户引导、审核 1、局部修补 | 约 15 分钟 | 有效工作。审核 1 抓到了真 bug（超大金额的 Decimal 精度） |
| 审核 2、3 和两轮修补 | 约 13 分钟 | **白跑**，原因是流程规则设计有缺陷 |
| 最后一轮第一步 | 205 秒 | DeepSeek 服务器故障，不是工作台的问题 |

结论：
- **短任务用单 Agent**，配上自动验收最快。
- **长任务、复杂任务、改错代价高的任务**才值得用规划加独立审核。
- 多 Agent 的价值来自"独立视角抓错"，不是"两个人干活更快"。规划和审核本身就是额外开销，组合模式天生就比单 Agent 慢。

### 2.2 审核者必须拿得到客观证据
审核 2 和 3 白跑，原因是：
1. 审核者在**只读沙箱**里，跑不了需要写临时文件的测试，只能说"无法独立确认"，然后判不通过；
2. 执行者再怎么修，也修不了审核者的环境，修补次数就这样被耗光了。

**原则**：审核要有一份"不靠任何一方自述"的证据。做法是由编排器在沙箱外运行测试，把结果交给审核者。

### 2.3 中途报错不等于失败
旧规则是：执行过程中只要出现过工具错误，审核就强制不通过。可实际上 Agent 中途改错一次、马上重试成功是常态（比如 `old_string was not found` 之后换个写法就成功了）。

**原则**：过程中的报错只作为参考；只有**最终的客观检查**（验收命令）失败才一票否决。

### 2.4 区分"成果有问题"和"环境验证不了"
如果审核者只是因为环境限制没法验证，就不应该退回给执行者去修，否则一定是空转。

**做法**：审核结果加一个 `verification_blocked` 字段。为真时任务暂停，告诉用户需要什么，**不计入修补次数**。

### 2.5 时间大多花在模型身上，编排器能省的是流程上的浪费
- 一轮执行通常要 3–7 分钟，绝大部分是模型在思考和调用工具。
- 编排器能优化的地方：等进程退出的空等、白跑的审核、无效的修补循环、重复的规划。

### 2.6 人要能随时纠偏
长任务一定会遇到"有新想法"或"发现方向错了"。所以需要两种引导：
- **排队**：这一轮结束后，带上用户的话继续；
- **打断并发送**：立刻停下当前这一轮（不是停止任务），在同一个会话里带上用户的话接着做。

引导轮不计入修补次数，之后照常审核，审核者也能看到全部引导内容。

### 2.7 输出上限：小任务续写，大任务拆解
"抱奶龙的流星告白动画 HTML"这个任务，组合模式和"仅 Harness"两次都失败了，报错是 `max-tokens`。
- **不是上下文爆了**：这一轮输入约 3.6 万 token，输出约 5.9 万 token，正好卡在 DeepSeek 思考模式的默认输出上限 64K 附近。
- **思考和回答共用一份输出额度**：max 推理强度下思考会写得很长，再加上想一口气写出一个大文件，就超出了上限。
- **Harness 只是框架**：输出上限由模型和服务商决定；无界面模式下被截断后不会自动续写。
- **对策**：小任务截断了就在同一会话里续写（限次数）；大任务先拆成几步、分文件写，每次写入不超过约 300 行。另外可以调高 `max_tokens`，或者降低推理强度。

### 2.8 产物和附件：本质都是本地路径
- 浏览器拿不到本地文件的绝对路径，也打不开本地文件。所以"打开文件"和"选文件"都要由本机后台代劳，并且只允许操作当前任务的文件夹和这个任务的附件。
- 可执行文件（`.exe`、`.bat`、`.ps1` 等）双击只在资源管理器里定位；要运行必须在右键菜单里明确选择并确认，因为运行它就等于执行 Agent 写的程序。
- 识图能力看 CLI 和模型：Codex 有 `--image` 参数，实测能识别图片颜色；Harness 的无界面 CLI 没有图片参数，只能拿到图片路径。所以要按"视觉 / 文本"标出每个模型的能力。

## 3. 实测数据

| 测量项 | 结果 | 说明 |
|---|---|---|
| Harness 回答 "hi" | 2.8–4 秒 | 很快 |
| Codex 回答 "hi"（原来） | 21.4 秒 | 模型约 10 秒，**进程退出约 11 秒** |
| 关掉 MCP | 21.4 秒 | 没有变化，MCP 不是原因 |
| 推理强度改成 low | 模型部分快了约 2.6 秒 | 收益不大 |
| 收到完成事件 1.5 秒后由工作台结束进程 | **11.5 秒** | 会话完好，`exec resume` 后仍记得上一轮内容（让它记住 4729，下一轮能答出来） |
| Codex 单轮输入 token | 约 1.7 万（缓存约 5 千） | Codex 自带的系统提示词和工具定义很大 |
| 组合模式中一轮 Codex 审核 | 68–138 秒 | 推理强度 xhigh |
| 组合模式中一轮 Harness 执行或修补 | 195–443 秒 | 推理强度 max |

**方法论**：先量再改。"Codex 慢是因为 MCP"这个猜测，一次对照实验就被推翻了。

## 4. 两个 CLI 的关键事实（做编排必须知道）

### 4.1 运行方式
- 两者都是**一次性进程**：启动、处理一个任务、退出。**运行中无法插话**，所以"引导"只能在两轮之间插入，"打断"只能靠结束当前这一轮。
- 续接会话：Codex 用 `exec resume <id>`，Harness 用 `--session-id <id>`。Harness 续接时必须带上原来的模型快照，避免中途换了通道。
- 两者都**不逐字输出**：Harness 的 `text` 事件在每一步完成时才发出。所以页面只能按步骤更新，没法像聊天客户端那样一个字一个字地出来。

### 4.2 权限档位（两边名称相同）
| 档位 | 含义 |
|---|---|
| `read-only` | 只读，规划和审核用 |
| `workspace-write` | 只能写工作目录，工作台的"一般权限" |
| `danger-full-access` | 不经过沙箱，工作台的"全部权限"，需要用户确认 |

- 审批策略：现在两边都设成 `never`，越权操作直接失败。Harness 支持 `--approval-policy ask|never`，但无界面模式下没有实时回复审批的通道。
- Harness 的 **ACP 接口**有"允许一次 / 拒绝"这样的实时审批请求，以后想做逐条审批可以从这里入手。

### 4.3 事件流（`--json`）
- **Harness**：
  - `session`、`status`（turn 和 step 的开始结束，step_end 里带 token 用量）；
  - `text`：Agent 正式说出的话；
  - `thinking`：思考内容，**丢弃**；
  - `tool_call`：包含 `tool` 和 `input`，也就是具体命令、路径、搜索模式；
  - `tool_result`：包含状态和结果文本；
  - `final`：最终回答。
- **Codex**：
  - `thread.started`、`turn.completed`（带 usage）；
  - `item.*`：`agent_message`、`command_execution`（带 `command` 和 `aggregated_output`）、`file_change`（带 `changes`）、`mcp_tool_call`、`reasoning`（**丢弃**）。

### 4.4 Windows 沙箱的坑：`SetNamedSecurityInfoW failed (Win32 5)`
- **原因**：Harness 的沙箱要给工作目录加一条权限并打上 Low 完整性标签，这要求对文件夹有**完全控制**（含 `WRITE_OWNER`）。D 盘根目录下新建的文件夹默认只继承到"修改"，所以会失败。
- **检测方法**：以 `WRITE_DAC | WRITE_OWNER` 的方式打开这个文件夹，成功就说明权限够。这只是试探，不修改任何东西。
- **解决办法**：给根目录 `D:\dede工作台` 加一条当前用户可继承的完全控制（需要用户同意），之后下面新建的子文件夹都会自动继承。
- **教训**：很多看起来像"性能问题"或"Agent 出错"的，其实是环境问题。

### 4.5 Codex 退出慢
回答完之后还要跑约 11 秒的退出流程。工作台在收到 `turn.completed` 1.5 秒后自己结束它的进程树，实测会话不受影响。

## 5. 编排器的设计原则（这次逐步确立的）

1. **复用本机 Agent 和它们原有的配置**，不让用户再填一遍 API Key，不读取凭据文件。
2. **模型配置做快照**：新任务开始时读取桌面配置，之后的修补和恢复都沿用这份快照，中途不偷偷换通道。
3. **有上限的自动修补**：最多 3 次质量修补；运行故障单独计数并暂停；没有无限重试；全面交给 Codex 接管必须由用户主动选择。
4. **权限默认最小**：规划和审核永远只读；全部权限要用户确认，并且跟着任务快照走；"用全部权限重跑这一轮"只放开一轮。
5. **客观检查优先**：验收命令的结果高于任何一方的自述。验收命令只能来自用户填写，或者根据项目文件识别出的固定命令，**不用模型生成的命令**。
6. **过程透明，但不泄露思考**：展示命令、路径、Agent 的说明和输出片段，先脱敏再截断；thinking 不显示也不保存。
7. **上下文接力**：切换模型时，由编排器保存完整聊天记录，只把对方还没看到的部分附在消息前面；太长时保留最近的部分，并指明完整记录文件 `对话记录.md` 的位置。
8. **"停止"与"打断"分开**：停止是结束任务；打断只结束当前这一轮，然后带上新输入继续。两者同时发生时以停止为准。
9. **删除要有边界**：删 Study 对话会连同它的文件夹一起删除，但只允许删 Study 目录下的直接子文件夹；删 Work 任务只删记录，永远不删用户的项目文件夹。

## 6. 实战使用建议

| 场景 | 推荐 |
|---|---|
| 问答、学习、整理文档 | Study，选 Harness 或 Codex |
| 小功能、小 bug | 仅 Harness 或仅 Codex，加自动验收 |
| 大功能、需求会变、改错代价高 | 组合模式，配合引导纠偏 |
| 方向错了 | 点"打断并发送"，不要干等一整轮 |
| 一般权限被拦 | 先确认文件夹权限，再考虑"用全部权限重跑这一轮" |
| 测性能、省额度 | 用 Codex（单轮约 11 秒） |

**写任务描述的技巧**：把验收条件写清楚，比如命令格式、输出格式、要写哪些测试。这样规划、执行、审核三方用的是同一把尺子。
